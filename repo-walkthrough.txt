Hi. This is a simple walkthrough of what this repository does and how its main logic fits together.

This project is a Visual Studio Code extension for STM32 microcontrollers. STM32 chips are small computers used in electronics. The extension helps turn the firmware source code into a program the chip can run, and it can also help flash and debug that program.

When Visual Studio Code opens the extension, the code in extension dot t s registers the available commands and checks whether the build tools are installed. Those tools include Make, the ARM compiler, and Open O C D, which is used to communicate with and debug the board.

When you choose Build, Build Task dot t s checks that a project is open and configured. The extension then gathers project information. It can read the Makefile generated by STM thirty two Cube M X, or use the extension's Y A M L configuration file. It scans the project for C, C plus plus, assembly, and header files, then combines those files with compiler flags, include paths, and chip settings.

Create Makefile dot t s uses that combined information to write the extension's Makefile. Make is the build coordinator: it calls the ARM compiler on the source files, links the compiled pieces with the linker script, and produces firmware files. The linker script matters because it tells the compiler where the program will live in the chip's memory.

This repository also adds dual-bank building. Some STM thirty two devices reserve two places in flash for application firmware, called bank A and bank B. The bootloader configuration describes that memory layout. A preset provides the default addresses and sizes, and the project can override those values.

The dual-bank generator creates a separate linker script for each bank. The build code then calls Make once per bank, with a different linker script, output folder, and vector-table offset. Separate folders prevent files from one bank being accidentally reused for the other.

After each build, the extension checks the firmware size against that bank's flash capacity. It counts code and initialized data, but not B S S, because B S S is stored in R A M while the program runs. It then copies the binary, E L F, and hex outputs into the configured output folder.

One subtle detail is the vector table. Cortex M chips use it to find interrupt handlers. The firmware needs to point it at the bank where that particular image was built. The extension checks the source code for this and warns if the setting looks wrong.

So, in one sentence: the extension discovers how your STM thirty two project is configured, generates the build files, asks Make and the ARM tools to compile it, and for dual-bank projects repeats that process for both memory locations.

Thanks for listening.
